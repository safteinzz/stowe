# AGENTS.md

Working brief for an AI coding agent, not documentation for people (the README covers that): the rules, invariants and gotchas needed to change this project correctly without rediscovering them.

## Hard rules
- Linux-first; Windows deliberately unsupported until it can actually be tested on Windows.

## Invariants and gotchas
- When checking whether a remote is available: **a folder existing proves nothing** - unmounting leaves the mountpoint dir behind, so a bare directory check can target the wrong disk. Proof is the remote's on-disk `.stowe/` marker plus the local record of where it is (`.stowe/remotes/<name>`); a known remote whose marker is gone must error, never be recreated.
- When touching the record of a remote (`.stowe/remotes/<name>`): it is the commit the remote was last known to be at, written by push and pull, cleared by `remote add` when the location changes, and made to follow the remote's own `refs/main` whenever a local remote is read (`remote::refresh_head` in `verify_reachable`, `remote add`, iremote). A foreign commit is recorded too, so the remote reads `diverged`. iremote's probe only reads: `App::reach_in` writes on the main thread, dropping a probe older than the last config change (`probe_seq`) and writing nothing while a job runs, since a push records its own head as it ends. `status`, `repos` and `irepos` stay offline and read only the record, and an s3 remote's record is written only by push and pull. iremote's plan pane leads with the mirror's drift (`mirror::drift`, which writes nothing and tells a case-folding filesystem by finding `.stowe` as `.STOWE`), counted by `App::plan_drift`.
- When touching `--mount` handling: the script is the sole authority - stowe runs it and trusts the exit code, no folder-based second-guessing. Scripts must be idempotent (instant no-op when already mounted).
- When changing mirror sync: plan against the mirror's *actual* files, not only its manifest - otherwise it can't repair a drive someone deleted or corrupted files on.
- When changing drift detection: judge drift against the commit being *pushed*, not just the recorded snapshot - otherwise adapt → commit → push dead-ends on the file that was just adopted.
- When touching any tree walk: `.stoweignore` (parsed in `src/ignore.rs`) applies to the working tree *and* to every mirror walk (`mirror_sizes`, `adapt`) - a phone regenerates `.thumbnails/` constantly, so junk that is ignored locally but not remotely reads as drift and demands `--force` on every push. Ancestors are checked, so a file inside an ignored dir is ignored even when the caller didn't prune. An explicitly named path (`stowe add junk.tmp`) is still staged, and stays visible to every walk after that because each one builds its `Ignore` with `keeping` the tracked paths.
- When changing mirror sync: a mirror's filesystem may ignore case (exFAT, a phone's storage), where a rename that only changes case does nothing and a copy onto a case variant rewrites the file under its old name. So a move onto a name the mirror already holds parks in `.stowe/tmp/` and lands after removals, folders are respelled whole, and two committed names that differ only in case are refused before the push. `names::rename_unportable` picks its safe names ignoring case and refuses one that would clash, since the check before the push has already run by then.
- When touching anything that writes a file from a remote: bytes are checked against their hash on the way (`scan::copy_verified`), because a same-size edit on a mirror is not drift and would otherwise come back as the old version.
- When touching scan/status: `status` never decodes audio; only `add` fingerprints (decoding dominates import cost), cached by size+mtime. The fingerprint is blake3 of the first ~30s of decoded PCM - survives rename/re-tag, not re-encode.
- When optimizing tree walks: keep `read_dir` + `DirEntry::metadata` (dirfd-relative stat; full-path stats are ~5x slower on deep FUSE trees) and keep the walk sequential - a FUSE daemon serializes, so parallel walking is *slower*. Only content hashing is parallel.
- When writing files to a mirror: names legal on ext4 can be unstorable on exFAT/NTFS (control chars etc.) - push probes the target FS empirically and offers a rename fix; never let a raw `os error 22` reach the user.
- tokio stays quarantined in the object-store remote code; the rest of the program is synchronous by design.
- When touching staging: `add::stage_all` and `add::stage_paths` call `kept::keep` before writing the index, so a text file of at most 1 MB that is UTF-8 with no NUL gets a copy in `.stowe/objects/<2>/<rest>` named by its hash, which is all istatus diffs against. Only hashes new since the index (or HEAD) are read, so `add -A` never rereads unchanged small binaries, and they are deduped first because two identical files in one stage race on one object. Text committed before copies were kept has none, and the pane says so.
- When touching file IO or showing an error: call `fs_err::`, never `std::fs::`, so a failure names the file and what was done to it, and show every error through `errors::words` (an `io::Error` alone through `errors::io_words`), never `{e}` or `{e:#}`, because that is what turns an OS error into words instead of `Permission denied (os error 13)`. `main` prints the CLI's errors through it, and symphonia gets the plain file from `fs_err::File::into_file`.
- When recording an entry's mtime: it is whole seconds, and a file written in the same second it was stat'd gets `model::UNTRUSTED_MTIME`, so a same-size edit later in that second is still hashed by the next scan (`scan::recorded_mtime`).
- When a TUI is up nothing may print: `scan::progress_to_screen` turns every `Progress` into the footer's line, and every long operation has a quiet core that returns a value (`push::push_one`, `adapt::adapt`, `convert::convert`, `restore::restore`, `add::stage_paths`, `unstage::unstage_paths`, `commit::commit`, `names::unstorable` + `names::rename_unportable`) under a CLI `run` that prints it. A new long operation gets the same split, or its output lands on top of the screen.
- When a core has to stop with something to show, it fails with a typed error the caller downcasts, never an `eprintln!`: `mirror::Drifted` (push or convert over drift), `mirror::Diverged` (push to a remote at a commit this repo lacks), `remote::Unseen` (push into an empty local folder with no record and no mount command, which an unmounted drive leaves too, so only `--force` writes there) and `mirror::Conflicts` (adapt) carry what they found; the CLI prints them, the TUI turns drift and divergence into the typed gate that offers `--force`, an unseen folder into a plain gate that does, and conflicts into an alert. `app/jobs.rs`'s `Unportable` does the same for names a drive cannot store, which the TUI offers to rename, and its `Loses` stops an adapt that would delete or overwrite files here (`mirror::plan_adapt`, then `apply_adapt` once the typed gate is answered, and only while the plan still loses exactly what the gate listed). A mount command's failure is `remote::MountFailed`, which keeps the end of its stderr for the alert, since the terminal it wrote to is covered again by then, and a cancelled one is a status line.
- When a TUI touches a remote with a mount command: run it through `tui::suspended` (the terminal handed over, SIGINT/SIGQUIT caught so Ctrl-C reaches only the child, by one handler installed once and switched by a flag, because unregistering a signal-hook handler leaves the signal ignored for good), then call `remote::verify_reachable` from the job's thread. Never `ensure_reachable` off the main thread: it runs the mount with the terminal still taken.
- When adding a TUI key that writes the config or the index: ask `busy` in `app/keys.rs` first. A running job writes both as it ends (a push records the remote's head, a stage writes the index), so it would undo the key's change, and `q` waits for the job for the same reason.
- When the drill reads history: `app/load.rs` walks it once per repo (`history::walk`, each commit read once) into `App::log`, and the commits pane, a file's versions (`hist`) and the scan's hits are all worked out from it. `hist` and `hits` hold indices into `log`, so `request_log` clears them with it; forgetting that is an index out of bounds the moment a refresh lands.
- When deciding whether a restore needs a gate: compare the working file's size and mtime with HEAD's entry, as a scan's cache does, never hash it on the input loop (a video would freeze the screen). A file unchanged since HEAD gets the plain gate when the commit some remote is known to be at holds that version, and the typed gate when none does, since a restore takes its bytes only from a remote; one with uncommitted changes gets the typed gate, a missing one none.
- When finding repos under a folder (`repos::find`): a repo has `.stowe/HEAD`, a mirror only `.stowe/refs/main`, so a backup drive inside the searched tree is never listed as a repo.
- When showing a remote's URL: show what the config holds through `paths::short_url`, never a resolved or canonical path, so a frame shows `~/drive` and not where the renderer's home is.
- When changing TUI keys: the shared vocabulary is `tui-modeless.md`'s; this project's own keys are `a adapt`, `m mount`, `v convert` on iremote (`↵ push`), `↵ difftool` (the editor when only one version of the file is here), `s stage`, `u unstage`, `space flip` and `S`/`U` for every row on screen (the scope and `/` decide which) on istatus, its diff scrolled with `ctrl-j/k` and panned with `ctrl-h/l`, `c create` making a commit there and a remote on iremote, `↵ restore` on a commit's changes. `d del` on istatus puts a row back as HEAD has it behind a typed gate (`status::discard`): the bytes come from a file of the same row (a move), the kept copy, or a remote whose last push holds them, and every byte is back before anything is unstaged or deleted.

## The demo rig
- `stage.sh` builds a fake home (an invented media archive and a drive to back it up to); `shots.tape` and `shots-short.tape` render the transcript stills, `plain.tape` the plain twins' stills, and one tape per interactive command (`history` / `status` / `remote` / `scan` / `repos`) its GIF, at 1056x664. The clips and `plain.tape` start from `./stage.sh story`: the reorganisation committed and pushed, one more commit pushed, one not, work in progress, and a second archive (`Podcast`) for `irepos`. `status` and `remote` commit and push inside their stage, so each tape builds its own. `demo/render.sh` renders them in a container (the image is `demo/Dockerfile`), so a machine needs podman or docker and nothing else: `./render.sh` runs every tape and `./render.sh <tape>` one, each in a container of its own that stages, records and tears down, and they write straight into `readme-assets/`.
- Two stills tapes because VHS fixes the frame size for a whole tape: `shots.tape` is the tall transcripts, `shots-short.tape` the handful-of-lines ones, and a shot in the wrong tape is a mostly empty picture.
- `stage.sh` redirects `HOME` and every XDG variable into `demo/home` and sets `GIT_CEILING_DIRECTORIES` there, because the stage sits inside this repository's working tree and without a ceiling a git-aware prompt would report *stowe's* branch and dirty count from inside a media archive. Its teardown unmounts everything under the stage before deleting, because a `--mount` remote can put a real drive or phone under that path.
- The fixtures: invented artists and shoots, `s3://example-archive/...` (RFC 2606), audio synthesised by ffmpeg so the fingerprint is fingerprinting real audio.
- Everything the rig creates lives inside `demo/home` (gitignored), the `stowe` symlink and the staged shell's rc included, so one guarded delete takes all of it.
- `paths::short` prints `~/drive` and `paths::expand` accepts it back, which is what keeps the stage's absolute path out of every frame. A long listing (`ls -l`) prints the renderer's user and group, so the mirror still lists names only.

## Overview
Layout:
- `src/main.rs` - the clap `Cmd` enum, the dispatch match, and the `--help` command list, which is rendered here (`help_template`) so the interactive verbs get their own `Interactive (TUI):` group; a name starting with `i` (but `init`) goes there.
- `src/commands/<verb>.rs` - one file per command, each exposing `run`.
- Domain modules at the top level: `repo` (the `.stowe/` on disk), `model` (commits, entries, manifests), `scan` (walking and fingerprinting the tree), `mirror` (playable remotes), `remote` (locating a remote and making it reachable), `names` (portability and the rename fixes), `ignore` (`.stoweignore`), `audio` (fingerprinting), `paths` (how a path is shown to a person, and `~` back to a path), `prompt` (yes/no questions), `time` (commit timestamps), `selfcmd` (`stowe self`), `kept` (copies of small text files in `.stowe/objects/`), `errors` (an error in words, OS errors included).
- `history` (what each commit changed, `walk`, the name search, a file's names across moves) and `repos` (finding repos under a folder and each one's state) serve both the plain `search`/`repos` and the TUIs.
- `src/tui/` - primitives with no screen knowledge: `input` (key predicates, `Accel`), `widgets` (`key_footer`, `Query`, `Modal`, gates, `Form` with pick fields, scrollbars), `highlight` and `difffeed` (the side-by-side diff, highlighted off the input loop), `difftool` (handed two files with `--no-index`, since there is no git repo), `suspended` for handing the terminal to a mount command.
- `src/app/` - the drill: one `App` with a `Level` stack (`Repos` → `Commits` → `Files`, with `Remotes`, `Scan` and `Status` as start levels, `Scan` stepping into `Commits`); `irepos`, `ilog`, `iscan`, `istatus` and `iremote` only pick the start level. `load` holds every background read, `patch` istatus's diff (a `git diff`-shaped text from kept copies, so `tui::highlight` draws it unchanged), `jobs` the threaded work and its boxes, `keys` one arm per level, `ui` one per level.

`stowe` is a Rust CLI on crates.io: git for the files git chokes on (music, photos, video, datasets). Content-addressed, linear history (one `main`, no branches, no content diffs). A remote is either a **mirror** (real playable folders on a drive/phone, bookkeeping hidden in a `.stowe/` beside them) or a **backup** (deduped blobs, e.g. S3). Local remotes default to mirror, s3 to backup; `--format` overrides, `convert` flips a remote in place. AGPL-3.0-only.
